# Deep Recovery V1 production package

`Deep.Protocol.Identity.DeepRecoveryV1` is the clean-break production recovery and account-authority
package in `Deep.Protocol`. The former `Deep.Protocol.Native` project, tests and dark solution were
removed; there is no alias, type forward, compatibility reader or fallback.

## Recovery phrase

- Entropy is exactly 256 bits from the platform CSPRNG.
- The phrase is exactly 24 words from the canonical English BIP-39 list.
- Encoding and checksum are BIP-39 compatible; input is NFKD-normalized and canonical output is
  lower-case words separated by one ASCII space.
- V1 intentionally has no user passphrase. The PBKDF2 salt is exactly `mnemonic`, avoiding an
  undeclared second recovery secret and ambiguous restore UX.
- Every non-24-word input rejects before derivation, including 12- and 13-word input.

The BIP-39 seed is not used directly as an account or device key. The final
contract is defined by the superproject `DEEP-CRYPTO-V1-DRAFT.md`;
HKDF-SHA-512 derives role-separated material from exact
`networkId16 || accountGenerationBE64`, where generation starts at one and zero rejects:

- account signing;
- device-certificate issuer signing;
- account revocation signing;
- reset-control signing;
- backup wrapping.

The permanent address-signing seed and 16-byte address-read capability instead use the fixed
`DeepGlobalAddressV1` context and therefore do not change with network or account generation.
The reserved `account-pq-signing-seed` label remains frozen in the specification but is deliberately
not derived or exposed by the V1 production capability: suite `0x0201` authenticates with Ed25519,
and no ML-DSA contract is active.

The sealed production capability exposes role-specific Ed25519 signing operations and defensive
public-key, public resolver-read-capability and network copies, not entropy, seeds or public
constructors. The resolver-read capability is intentionally shareable because canonical `DID1`
and its Bech32m form include it; the underlying derivation seed remains sealed. Device keys remain independently
generated CSPRNG material. V1 never derives device keys from the phrase and never converts Ed25519
material to X25519. `Dispose` deterministically zeroes every owned managed secret buffer; callers must
still avoid logging, telemetry, clipboard persistence, screenshots, crash dumps, and unnecessary
immutable string copies of recovery data.

## Post-quantum status

This bounded identity package creates no PQ-provider readiness claim. The release-target specification selects hybrid
X25519+ML-KEM-768 and Triple Ratchet semantics, but activation remains blocked
on provider/license/ABI, independent implementation, vector, platform,
protocol-state and external-review gates. The reserved account PQ role does
not imply ML-DSA authentication in suite `0x0201`.

## Evidence

- The embedded English word list is pinned by SHA-256 and count.
- A checked-in vector is generated by an independent Python standard-library PBKDF2/HKDF oracle.
- Tests cover checksum/word/count rejection, normalization, context and role separation, defensive
  copies, zeroization, and the absence of public seed/constructor surfaces.
- Focused production tests cover the independent vector, permanent-address invariance, account
  generation floor, role-key substitution, public API shape and deterministic disposal.
- Consumer activation and destructive state reset remain separate authorized work; there is no
  runtime negotiation or fallback to the removed dark package.
